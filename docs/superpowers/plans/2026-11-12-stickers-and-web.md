# 计划书 · 表情包与上网

> 2026-11-12。来源：「发送表情包的功能，和一个可以让她上网了解事情的功能」。
> 结论先说：**这两件事共用同一个机制**——在回复里留方括号指令，由我们执行。不用接 tool。

---

## 一、要什么

1. 她发得出表情包。不是随机图，是**她自己的**图。
2. 她能上网了解事情。不是只有主动搭话时顺手查一次。

---

## 二、地基盘点（已经有的）

| 能力 | 现状 | 证据 |
|---|---|---|
| 发图 | ✅ 通了 | `c02ace6`：OneBot image 段，URL / 本地 / base64 都行，5MB 上限。真机 `retcode 0` |
| 搜索 | ✅ 有 | `src/search.js`：Tavily，事实缓存 24h，每天 5 次额度 |
| 收图 | ✅ 大图也能读 | `f69e63a`：20MB / 101 帧的 GIF → 4 帧 119KB |
| **缺的** | ❌ 她做不了决定 | 回话是纯文本，没有任何出口能说「我要发图」「我要查一下」 |

所以缺的不是能力，是**出口**。

---

## 三、为什么不用 tool

我们的会话是自建循环（`session.js`）：一次 `complete()` 拿一段文本，不跑 tool。

接 tool 意味着把整个循环换成 agent loop：多一次模型往返、多一层协议、多一处会随 DSH 升级而坏的地方。为了「发张图」不值得。

**改用：在她的回复文本里留方括号指令。**

```
她说：不用猜了[表情:无语]
我们：① 发文字「不用猜了」  ② 发一张「无语」
```

一条协议管两件事，两个词：「表情」「查」。

## 四、① 表情包

### 图源：账号的收藏表情（改过一次）

第一版计划是「本地一个目录，文件名就是含义」。**已作废**，因为实测发现：

```
fetch_custom_face_detail → retcode 0，13 张，每张带 url
```

上次探是空数组，不是网关没实现，是号里当时确实没有收藏。这是他存了之后才通的路。

所以现在：**收藏表情就是要用的那一批**——它自带「他喜欢什么」的语义，比任何自建目录都准。

唯一缺的是 `desc` 全是空的：她不知道哪张是什么意思。所以同步时用视觉模型给每张起一个 ≤6 字的名字（一次），存进 `stickers.json`，之后不再重复。

- 名字的来源是一次视觉调用，不是文件名
- 起不出名的那张就留着不用（`pickSticker` 只认有名字的）
- 仍然不联网搜图；仍然不用本地目录（那条路留着，哪天收藏满了再说）

**不下载落盘**：发出去直接用 url，网关自己去取。省一次读盘、一次编码，也不占磁盘。

### 她怎么知道有哪些

上下文加一块：

```
【你手上的表情】无语、委屈、猫猫头（想发就写 [表情:名字]，别把方括号念出来）
```

从 `stickers.json` 现读，`at = 现在`——符合 `fresh.js` 的规矩（现算的块不需要 ttl）。
**只给名字，不给 url**：地址是机器细节，名字才是她的梗。

### 挑哪一张

1. 她写 `[表情:委屈]` → 先精确匹配文件名
2. 精确不到 → 包含匹配（`[表情:有点委屈]` → `委屈`）
3. 还是不到 → **不发**。宁可这次没有表情，也不要拿一张不相干的顶替——那比没有更糟。

### 频率与风控

| 上限 | 值 | 为什么 |
|---|---|---|
| 每条回复 | 1 张 | 连发多张不像人，像刷屏 |
| 每分钟 | 2 张 | 连发表情会触发 QQ 风控（dsh-qq-sticker 作者明确写过这个坑） |
| 每小时 | 10 张 | 同上 |

超限就把标记丢掉，文字照发。

## 五、② 上网了解

### 触发

`[查:关键词]`

### 搜索结果怎么给——**这是和现在最大的区别**

现在是「压成一句 50 字事实」（`squeezeFact`）。用在「他想知道一个数」上够用；用在「她想了解一件事」上不够——那会把一件事压成一个结论，而她要的是了解，不是答案。

改成给她材料：

```
【你刚查到的】（3 分钟前查的，来源：zhihu.com、wikipedia.org）
- 杭州明天小雨转阴，8~14℃，东北风 3 级
- 未来三天有冷空气过境，周五最低 5℃
```

2~3 条，每条 ≤120 字，带来源域名。**她自己组织语言，我们不替她总结。**

### 一轮变两轮

`[查:...]` 出现时：

1. 先不发文字——她还没说完
2. 我们搜索（1~2 秒）
3. 结果作为 context 再要一次回复
4. 发最终那段

代价：多一次模型调用 + 2 秒。只在她真的要查时发生，不是每轮。

### 额度

沿用现有那套：`canSearch` / `noteSearch`，每天 5 次，`cleanQuery` 先清洗。
**查不到就说查不到**——`search.js` 已经有这条规矩，不在这里另发明。

## 六、实施记录（①②③ 已落地）

| 步骤 | 落在哪 | 备注 |
|---|---|---|
| ① 解析层 | `src/actions.js`：`parseActions` | 全角半角冒号都收；标记从文本里剔掉，他看到的只有话 |
| ② 表情库 | `src/stickers.js` + host 的 `syncStickers` / `sendSticker` | 启动时同步收藏、视觉起名、按名字挑、每分 2 张每时 10 张 |
| ③ 搜索回灌 | `search.materialLines` + `session.retry` + companion 的 `refine` | 一轮变两轮，只重来一次 |

**阈值**：名字 ≤6 字（起名截 8）、列表 ≤160 字、材料每条 ≤120 字最多 3 条。

**一个坑**：`refine` 必须把拼好的字符串传给 `session.retry`。传对象进去会被 join 成 `[object Object]`，
第二次调用的 system 里就没有材料了——而「发出去的是第二版」这条断言照样过，只有断言 system 内容的那条能抓住。

## 七、风险与回滚

| 风险 | 缓解 |
|---|---|
| 她把方括号念出来 | 人格卡加一句：想发表情/想查东西就用 `[表情:xx]` `[查:xx]`，别念出来 |
| 她每轮都想发、每句都想查 | 额度（5 次/天）+ 每条回复最多一张 + 查一次要等 2 秒，她自己会觉得贵 |
| 文件名被当成内容注入 | 只取 basename、去扩展名、截 20 字；路径绝不进上下文 |
| 发图失败（网关不认某种格式） | 只 `warn` + 记日志，这一轮文字照发——绝不整轮哑掉 |
| 搜索结果太长挤掉别的上下文 | 每条 120 字、最多 3 条，走 `fresh.js` 的块 + ttl |

**回滚**：解析层是纯函数，删掉调用就回到纯文本；表情目录是数据不是代码，清空即失效。搜索回灌是 host 里一个 if。

---

## 八、验收

- 单测：解析（含转义、嵌套、多个标记）、匹配（精确 / 包含 / 未命中不发）、频率上限
- 单测：搜索结果渲染（带来源、有长度上限、过期不注入）
- 真机：说「给我个委屈的表情」→ 她发文字 + 一张委屈
- 真机：说「查一下杭州明天天气」→ 两轮之内给出带来源的答复，而不是「我不太清楚」

---

## 九、这份计划不解决什么

- **不解决「她怎么知道这张图好不好笑」**：文件名是她唯一的依据。文件起名别太抽象。
- **不解决收藏表情**：网关那边是空的，不是我们的活。
- **不解决多步研究**：一次只查一件事。她要「先查 A 再根据 A 查 B」，得是另一个量级的东西。
- **不解决「她该不该主动发」**：这一版只响应她回复里写的标记，不做「她自己想发就发」。
