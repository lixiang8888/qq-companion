# 感知记忆（perception memory）设计

日期：2026-11-15 · 状态：待你确认 · 项目：qq-companion

## 一、这是什么，为什么现在做

她现在只有语言记忆。她发过的图、她看过的画面，只在记忆卡里留下一句画面描述（`detail`），
而且那个字段目前没有任何地方读它——等于图看完就没了。

要做的是**第二类记忆**：她**看到过**的东西。属于"感知"而不是"听说"，有像素、有画面、
有"当时我在场"的时间地点。现在最小可用是图；将来活动空间变大（自己看屏幕、看网页、
看视频），同一套东西直接接上去，不用重写。

为什么是现在：图只在到达那一轮拿得到（QQ 图链带 rkey 签名会过期），不落盘就永远没了。
越晚做，丢的图越多——现在她已经丢了一年的。

## 二、目标 / 非目标

**目标**

1. 图落地存本机，能再取出来看（原图 + 缩略图）。
2. 能用一句人话把它找回来（"那个粉头发的举牌子"），不是只能按文件名。
3. 找到之后**由图确认是哪一张**再说话（模型真看了缩略图），而不是纯文字猜。
4. 不挤占记忆卡的 2200 字预算。
5. 数据结构里给向量留位置，接 embedding 时不用改 schema。

**非目标**

- 不做以图搜图（要 CLIP，你的图是二次元/表情包，通用 CLIP 效果差，值不回成本）。
- 不做跨会话的"实体档案"（把同一个人的每张脸归到一个人名下，像 vemem 那样）。
- 不做桌面截图感知（`screen` 现在只读窗口标题，不截屏）。
- 不做图片生成的记忆（她没这个能力）。

**反面目标（做到这些算失败）**

- 找回来的图不是他说的那张 → 还不如说"我想不起来了"。
- 每轮都跑一次视觉复核 → 一天烧掉几十次调用。
- 图库无限长大把磁盘塞满。

## 三、约束（查过代码和真实数据）

- 视觉模型可用：`deepseek-flash`，走 `https://api.deepseek.com/chat/completions`，
  已在 `vision.js:79 describeImage()` 里跑了一年，收 `dataUrls` 数组（可一次看多张）。
- **DeepSeek 没有 embedding 接口**（bifrost / gomodel 两处文档都写了），所以第一版不用向量。
- 缩图用现成的 `vision.js:143 shrinkImage(bytes, {max, quality})`（sharp）。
- 落盘用现成的 `createJsonStore`（写临时文件 + rename、5 分钟一次的 .bak、坏文件改名留证）。
- 检索复用 `memory/search.js` 的 `search()`——它只要求记录有 `text`，其余字段缺了有默认值。
- 现有真实数据（逐条解析过，不是 grep 出来的）：17 条老记忆正文里是整段画面描述、
  9 条是另一种旧格式、4 条是"看不到内容"的占位、`detail` 字段 0 条。迁移是独立的可选一步。

## 四、三条路，选了哪条

| 方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| **A 结构化语义槽 + 模型复核** | 存图时让视觉模型输出结构化标签；检索先文字召回候选，再把缩略图交给模型选 | 每次检索多一次视觉调用 | **选它**：对齐靠真看图，比任何向量准；零新依赖 |
| B 文本向量 + 复核 | 描述编码成向量，余弦召回，再复核 | 要额外 embedding 源（Ollama 或新 key） | 对齐的是"描述"不是画面，且多一个服务 |
| C 真·跨模态向量（CLIP） | 图和文字同一空间 | onnxruntime + 200~600MB 模型；通用 CLIP 对二次元最差 | 你的图主要是二次元/像素/梗图，选型还得再赌一次 |

A 的弱点（多一次调用）恰好是它最准的地方：**她每次都真的在看图**。B/C 路径留在
`vec` 字段里，将来接了 embedding 直接当召回层，A 的复核层不用动。

## 五、怎么存

### 文件布局

```
<dataDir>/perception.json                    索引（单文件，createJsonStore）
<dataDir>/perception/2026-11/p_3f9a1c77.jpg        原图
<dataDir>/perception/2026-11/p_3f9a1c77.thumb.jpg  缩略图（≤320px，quality 60）
```

### 一条记录

```json
{
  "id": "p_3f9a1c77",
  "sha": "3f9a1c77a1b2",          // sha256 前 12 位，去重用，也是 id 的来源
  "at": 1794661272605,            // 什么时候看到的
  "source": "his",                // his = 他发来的；hers = 她自己看到的（预留）
  "scene": "chat",                // chat / screen / web / sticker（后三个预留）
  "file": "perception/2026-11/p_3f9a1c77.jpg",
  "thumb": "perception/2026-11/p_3f9a1c77.thumb.jpg",
  "pixels": true,                 // 原图还在不在（淘汰后变 false，缩略图仍在）
  "w": 640, "h": 640, "bytes": 81234, "mime": "image/jpeg", "frames": 1,
  "title": "粉发女孩举着 love 牌子",   // ≤30 字，注入用这一句
  "desc": "画面中粉色头发…（≤400 字）",  // 完整描述：给将来的她/迁移用，不注入
  "slots": {                      // ≤5 类，每类 ≤4 个词
    "who": ["女孩", "二次元"],
    "what": ["牌子", "爱心"],
    "where": [],
    "action": ["举着", "摇头"],
    "look": ["粉色头发", "浅蓝发饰", "像素风"]
  },
  "feel": { "v": 0.6, "a": 0.35 },   // 当时她的心情（有 mood 才写）
  "heat": 0.35,
  "memoryId": "m_8fffba40",       // 尽力而为，可为 null（见 §七）
  "hits": 1,                      // 被找回去过几次
  "lastHitAt": 0,
  "vec": null                     // 预留：将来接 embedding 放这里
}
```

### 写入流程（图到达那一轮）

**写在哪儿**：字节在 `withImages` 里（`host.js:901`），但 `feel`/`heat` 要等 `appraise`
（`companion.js:39`）、`memoryId` 要等 `memoryBlock` 建卡。而 `mailbox` 只保留**最后一条**
消息对象（`mailbox.js:50`），所以他 3 秒内先图后字，`withImages` 返回的 id 会丢。

所以分两步，中间用一个内存队列接：

1. `withImages` 拿到字节 → 嗅探、抽帧（现有逻辑不动）→ 调用一次视觉模型（见下）→
   把 `{bytes, thumbBytes, mime, w, h, frames, title, desc, slots, at}` 推进
   `pendingPerceptions` 队列（模块级数组，不落盘）。
2. `memoryBlock` 里（已经有 `mood`/`heat`，且这批记忆卡刚好建完）→ `drainPerceptions()`
   把队列取空：算 sha、去重、写盘、写索引记录，`feel`/`heat` 用当前值、
   `memoryId` 用这一轮新建/命中的那条记录 id（拿不到就 null）。
   队列里 `at` 超过 2 分钟的条目直接丢弃（异常路径的保险）。

**一次调用，三个字段**。提示词要 JSON：

```json
{"title":"≤30 字","desc":"一两句话的画面描述","slots":{"who":[],"what":[],"where":[],"action":[],"look":[]}}
```

`desc` 是必须的：这一轮的正文（`withImageText`）和 `IMAGE_NOTE` 正则（`host.js:205`）
全靠它，**不能为了拿槽把描述弄丢**。解析失败 → 整段回复当作 `desc`、`title` 取前 30 字、
`slots` 留空——**绝不因为解析失败就不存图**。

3. 去重：算 `sha`；已有同 `sha` → 只 `hits++`、`lastHitAt`、`at` 不新增记录。
4. 索引落盘。记录上限 `MAX_RECORDS = 4000`。

### 容量与清理

两条独立的规则，都要：

1. **容量**：总量上限 `MAX_PIXELS_BYTES = 2G`。超了按 `lastHitAt`（没被找回过就按 `at`）
   从老到新删**原图**，记录保留、`pixels:false`。缩略图很小，一律保留——
   "记得是什么"比"能再看清"便宜得多。
2. **冷清理**（这才是 11-14 定的 heat 三档在图片上的落点）：满足全部条件才整条删掉
   （原图 + 缩略图 + 记录）——`hits === 0` 且 `at` 超过 90 天 且 `heat < 0.35`。
   那一刻很重的图（`heat ≥ 0.35`）不受这条管，只受容量管。
   这样"热的那次"长期留着，"随手发的截图"三个月后自己消失。

- 面板显示：`图 N 张（原图 M 张，占 X MB）`。

### 隐私

- 图只落本机磁盘，不上传任何第三方；出去的只有现有两次调用（描述、复核）里的图片字节，
  和今天发图看图的行为一样。
- `perception.json` 里只存路径，不存 base64。

## 六、怎么检索（这是"复杂语义对齐"的落点）

`recallPerception(query, { now, limit = 2, recheck = true })`

**第一段：文字召回（便宜）**

拼 `text = title + desc + 所有 slots 的值`，走现成的 `search()`。取 top 5。
`top1.score` 低于门槛就返回空——**宁可不提，不硬凑**（这条是"不编"的延伸）。

**门槛不是 1.0**：`search()` 把 BM25 乘了重要度（缺省 50 → ×0.75）和清晰度
（缺失 → ×0.5），所以分数整体被压到三成多。**先跑测试定标**：拿几条假记录，把"该命中"
和"不该命中"的分数打出来，门槛取在两者中间（初始值按 0.35 写，测试里校准）。

**第二段：模型复核（贵，有闸）**

把 top N 张的缩略图（最多 4 张，`dataUrls` 一次给）和他的原话一起发：

> 这几张图里，哪一张是他说的那件事？只回一个数字，第几张就从 1 开始数；都不是就回 0。

回 `{"pick":2}` → 用第 2 张。**回 0 → 这一轮什么都不提**（模型说都不是，硬塞一张错图比说想不起来糟）；
只有复核调用本身出错/没有 key 时，才退化成"只用召回分数最高的那张"。

闸门：复核 ≤5 次/小时（内存计数，重启归零）；超了只做第一段。

**什么时候触发**

**不看关键词，每轮都搜。** 旧版靠「图/照片/那张」触发是错的：发完图之后聊十分钟别的，
他那句里一个字都不带「图」，她就不会想起来——而他要的正是"该想起来的时候想起来"。

于是每轮都跑一次文字召回（4000 条以内是几毫秒，不调模型），门槛决定噪音，词汇表不再参与判定。

**近窗口：不检索，直接带完整描述**

最近 **24 小时 ∪ 最近 30 轮对话**里的图（并集，谁更近用谁），每轮直接注入，**最多 3 条**。
这几天发的图不需要"找"，它们还是当前话题的一部分，所以用**完整描述**而不是标题。
这条解决的就是「刚发完图、接着聊别的、她却不提那张图」。

**老图（没有原图、只有描述）**

也参与召回：候选里有 `desc` 就算数。选中之后**跳过复核**（没像素可看），直接注入一句
「你发过一张图，当时记的是：…」。这是"真正忘了的时候用文字把图找回来"的兜底。

**重看图片：把像素贴回她的回复调用**

判定"她该当场看一眼"时，不注入文字，而是把那张图放进这一轮的 `images`：
他这轮**没带图** + 检索分数 **≥ 0.4** + 那条**有原图**。每轮最多 1 张，现场从原图缩到 512px 再给。

这是他明确要的那条：「有任何需要的时候重新看一遍图片」。代价是那一轮多几百 token，
所以只在"分数够高、而且他自己没发图"时发生。

**注入**

独立一块，**不进记忆卡 2200 字**：

```
【你看到过的】（图片，不是他这一轮发的；你当时真的看过）
- 11-14 21:03 他发的：粉发女孩举着 love 牌子（那会儿我挺高兴）
- 21:40 他发的：一张截图，上面是报错信息
```

近期那几条用完整描述（每条 ≤80 字），检索命中的用标题（≤60 字）。整块封顶 3 行。
带 `at` 和 `ttl`（5 分钟），走 `fresh.js` 的 `blk()`，和现有上下文块一个规矩。

## 七、和现有记忆卡的关系

- 记忆卡正文仍是 `他发了一张图` + 他的原话（不变）。
- 记忆卡的 `detail` 字段**停用**：画面归感知记忆。它的三档语义（heat ≥0.6 留、
  0.35~0.6 只留 gist、<0.35 淡掉）改由 §五 的「冷清理」承担，不再两处各管一半。
- `memoryId` 是**尽力而为**：`remember` 按正文去重（`card.js:259`），而纯图消息正文都是
  「他发了一张图」，所以连着发几张纯图只会有一条记忆卡记录，多张图共享同一个 `memoryId`，
  也可能为 `null`。**不要**为了补这个链接去改记忆卡的去重规则——那会让「他养了猫」和
  「明天考试」也开始合并。
- 老数据迁移（**单独一步，要你点头才跑**）：逐条解析出来是 **17 条**整段描述 +
  **9 条**另一种旧格式 + **4 条**「看不到内容」占位（我之前说的 34/20 是错的——
  `Select-String` 把每条记录的 `text` 和 `quote` 各数了一次）。
  迁移做法：把旧描述写进感知记录的 `desc`（不用调模型，`slots` 留空、`title` 取前 30 字），
  记忆卡正文换成 gist。**原描述不丢**——它进 `desc`，不是被删。

## 八、测试（不联网）

1. 槽解析：合法 JSON / 带代码块围栏 / 完全不像 JSON（整段当 `desc`、`slots` 空，仍存图）。
2. **描述不丢**：解析成功时 `desc` 必须有值（`withImageText` 和 `IMAGE_NOTE` 靠它）。
3. 去重：同 sha 第二次不新增记录，只 `hits++`。
4. 召回：给三条假记录，问"粉头发的"命中正确那条；无关的 query 返回空。
5. 复核：假 fetch 回 `{"pick":0}` → 不注入；回 `{"pick":2}` → 注入第 2 条。
6. 限流：第 6 次复核不走模型（只做第一段）。
7. 容量：超限 → 最老的原图被删、记录留、`pixels:false`。
8. 冷清理：`hits=0` + 超 90 天 + `heat<0.35` → 整条删；`heat=0.8` 的同龄记录不动。
9. 队列：`withImages` 推进去的条目在 `memoryBlock` 里被取空，`feel`/`heat`/`memoryId` 填上；
   `at` 超过 2 分钟的条目被丢弃。
10. 注入块：格式对；单独 block，不进记忆卡 2200 字。

## 九、留给实现者的（我拍的小决定）

- 槽就五类 `who/what/where/action/look`，先跑一周看够不够，别一开始设计十类。
- 召回门槛初始 0.35（不是 1.0，理由见 §六），测试里定标后可调；限流 5 次/小时。
- 动图存**整段 GIF**（那就是她看到的原件），`frames` 记的是它一共有多少帧。
- 缩略图 `max:320` 而不是 512：复核时模型只需要看清"是不是那张"，不需要细节。
- **重看图片（v2 起）**：他这轮没带图、检索分数 ≥0.4、那条有原图 → 把图缩到 512px 贴进回复调用；
  每轮最多 1 张。v1 曾决定"不贴"，因为当时只考虑"用一行字代替看图"，漏了"想不起来的时候要重看"。

## 十、风险

- **复核认错图**：模型可能选错。缓解：找不到就退回分数第一，且注入时写"你当时真的看过"，
  不写"就是这张"。
- **成本**：每张图 1 次视觉调用（今天已经在付）+ 检索偶尔 1 次。限流兜底。
- **2GB 上限**：按他发图的频率，可能要半年才碰到；碰到了只是清原图，不是清记忆。
- **她不会真的重看像素**（v1，见 §九）：找到图之后，她拿到的仍是一句话，不是画面。
  够不够用要真聊几天才知道；不够再加"把缩略图贴回回复调用"。
- **队列是内存态**：进程在"图已下载、记忆卡还没写"之间崩掉，那张图就丢了。
  影响一个回合，不损坏已有数据。
