# 记忆检索评测（基线）

> 这不是论文，是一把尺子。**先有数字，再谈改进**——否则「感觉更好了」就是唯一的标准。

评测本体在 `test/memory-eval.test.mjs`，24 条固定记忆 + 10 道命中题 + 5 道无关题 + 3 道诱捕题。
`npm test` 里会一直跑，数字变差会红。

## 基线（2026-11-01，第一次测）

| 指标 | 结果 | 说明 |
|---|---|---|
| 命中 @3（检索） | **9/10 = 90%** | 期望记录出现在 `search()` 前 3 |
| 注入完整率 | 10/10 | 命中的那条真的进了 `rankForPrompt()` 前 14 条 |
| 无关题误召回 | **0/5** | 问「股票怎么买」不硬凑任何记忆 |
| 诱捕 | 0 次凭空出现 | 问「他前妻叫什么」，召回里不会冒出「前妻」 |

唯一没命中的是 **`晚上想吃什么锅` → `火锅`**：二元切词下「什么锅」和「火锅」没有一个共同的二字窗。
这是切词的固有限制，**不打算修**——加单字兜底会立刻污染无关查询（`dsh-neuron-memory` 也是因为这个
才把 `noFallback` 设成默认）。真实对话里说「火锅」就能命中。

## 评测暴露出的两个真问题（都已修）

1. **「他妈住院了」被「他手机号换了」判成同一件事**——两条只共享「了，」这个**标点**窗，
   于是旧的被覆盖、再也注入不出来。命中率一度因此虚高到 8/10（记录少了，排序自然好看）。
   修法：两字窗必须**全是文字/数字**，标点不算依据。
2. **命中率一开始是按 `rankForPrompt` 前 3 算的**，而它的顺序是
   「锚点 → 身份类 → 查询命中 → 按价值」——只要卡里有 2 条身份类，查询命中就永远到不了前 3。
   这不是 bug，是刻意的排序（身份类不许被预算挤掉）；错的是指标。改成两条：
   **检索命中看 `search()` 前 3**，**注入看它进没进她要看的 14 条**。

## 以后改检索时怎么用

```bash
node --test --test-isolation=none "test/memory-eval.test.mjs"   # 快，只跑评测
npm test                                                        # 全量
```

- 数字**变差**：先怀疑自己，再怀疑指标。
- 数字**变好**：把改动前的 9/10 记在这里，别只写「更好了」。
- 想加题：往 `HITS` / `NOISE` / `TRAPS` 里加，**不要**为了让测试变绿去改期望值。

## 还没测的

- **长程**：400 天后还剩不剩得住（`test/long-run.test.mjs` 测的是衰减，不是召回）。
- **噪声率**：一次注入里有多少字是跟这一轮无关的（neuron 用「每千字符命中数」衡量，我们还没有）。
- **模型会不会编**：诱捕只能证明「召回里没有」，证明不了「她说出口的话里没有」。那要靠人判。
